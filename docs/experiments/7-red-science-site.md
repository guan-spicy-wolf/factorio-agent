## 1. 纸上分析：放置规则的几族（规则 1）

要放的东西：两个矿区是锚定的（位置由矿决定）；自由单元有两条冶炼列、一条红瓶链、两个煤源夹具、一个汇、一个电源，共 7 个；链路 8 条。放置的输入只能是契约（口的格、朝向、`space`、道、速率）、地形快照（可建、资源、已占）和已放单元的占格。

| 族 | 做法 | 上限 / 缺陷 | 取舍 |
| --- | --- | --- | --- |
| A. 手写锚点 + 螺旋（现状） | 人给每个单元一个锚点，就近找空位 | 锚点就是坐标，违反验收；锚点偏一格就可能把下游堵死 | 排除（任务书明确） |
| B. 链路驱动的贪心：按依赖顺序逐个放，候选位按"估算带长"排序，取第一个放得下的 | 每个自由单元的代价 = Σ(到已放邻居口的估算带长 + 转弯 + 绕回惩罚) + 占资源格惩罚；候选来自邻居口周围的窗口 × 4 个朝向 | 贪心：先放的单元可能挡住后放的；估算不看障碍，路由器可能失败 → 失败时该单元换下一个候选（有界回溯）。对 3 层 7 个单元的站，代价函数的局部最优与全局最优差距 = 几格带长，不影响达标 | **选它** |
| C. 全局优化（CP-SAT/ILP 同时定所有单元位置与朝向，最小化总带长） | 最优（相对估算） | 要把足迹 × 地形编码进模型（每单元数千格 × 候选位），建模远大于求解；最优仍只是估算意义上的，路由器照样可能失败；本站规模收益 = 几格带 | 排除（收益不抵成本；留作大站的方向） |
| D. 容器（`Column/Row` 组合）：把"冶炼列 + 它的煤源 + 电"作为一个复合单元整体放 | 组合内相对位置固定，省掉几次放置 | 组合内的相对位置仍要有人定或有规则定——规则一样能逐个放；夹具已经是"贴口放"（`place_port`）；容器只在**需要重复同一组合**（n 条并列冶炼列 + 平衡器）时才省事，红瓶站没有重复结构 | 排除：这就是对"容器要不要"的回答（§末节） |
| E. 力导向 / 模拟退火 | 不需要依赖顺序 | 随机，特征化表不可复现；仍需碰撞检测与路由器验证 | 排除 |
| F. 顺流放置：下游口与上游口共线（零转弯），侧向汇入则错开一行 | 直连时最优（直带） | 是 B 的特例：B 的代价里转弯惩罚 = 0 就是共线；单独做一族没有新能力 | 并入 B 的代价函数 |

B 里几个"判断题"（算法给不出唯一正确答案、本质是偏好）先定默认值，记录里标出：

1. **带长预算**（下游离上游口多远算"合理范围"）：窗口半径 = 单元长边 + 若干格。取太小放不下就扩一倍再试。
2. **占资源格的惩罚**：冶炼列压在矿上并非违法（基线就压着），但挡住以后采矿；记作每格 `Costs.resource` 同一常数。
3. **放置顺序**：锚定单元先；然后反复取"已有邻居放好的未放单元"里（非夹具优先，已放邻居多者优先，链路速率大者优先）的一个。
4. **并列两个上游时的锚点**：代价是两条链路带长之和，中点附近自然最低——不用单独定义。

预期：B 在本站上应一次放通；若路由失败，最可能是冶炼列被放到两个矿之间挡住了链，靠候选回退解决。

### 迭代 2：按缓冲填充时间定预热；同物料口合并判定（04:35–04:44）

改动：

- `site_sweep.flows(site, gd, rs)`：两遍流量——正向算每个单元的产能上限（自身吞吐、各输入能收到的量 ÷ 该输入口在契约里的"每单位产出的份额" = 输入口 `rate` / 输出口 `rate`），反向算实际（只做下游取的量；汇取一切）。`predict` 建在它上面。

## 4. 容器要不要？

**不要。** 红瓶站是三层七个自由单元，`SitePlan`（锚定单元 + 自由单元 + 链路）加顺流放置就把它放通了，而且一次放通、没有回退。容器能给的只有"组合内相对位置固定"——规则逐个放一样得到（煤源贴在列的口旁、汇贴在链的口后），还不需要人先设计组合。容器在以下情形才值得：同一组合重复 n 次（并列冶炼列 + 平衡器分流），那时"把一组当一个足迹放"比逐个放省很多候选评估——而平衡器明确在本任务范围外。`docs/design.md` 已按此修订。

## 5. 放置规则的输入；哪些是判断题

**输入**（全部来自契约、地形快照、已放单元）：

- 链路两端口的格、朝向、`lane`、`space`（决定带从哪格出、到哪格进，与路由器同一判据 `link_mode`）；
- 两端口的 `rate` / `MinRate`（放置顺序里"大流量先放"、以及按下游契约定上游规模）；
- 地形的可建格与资源格（足迹 + 1 格边距要可建；占资源格有代价）；
- 已放单元的占格与它们口前的保留格。

**判断题**（算法给不出唯一正确答案，应交给 agent 或由人给偏好；本任务用了默认值并在 `PlaceCosts` 里显式写出）：

1. 带长预算：下游离上游多远算"合理范围"（窗口 = 单元长边 + 12，放不下扩一倍）。
2. 占矿的代价：压在矿上不违法但挡住未来采矿；每格 2 个带格的代价是偏好。
3. 转弯与绕回相对带长的权重（2 和 2）。
4. 放置顺序的优先级（非夹具 > 已放邻居多 > 流量大）；顺流顺序本身我认为是算法题（有多个生产者的单元必须等它们都放好）。
5. 要不要为了让下游更近而牺牲上游与矿的距离（贪心不回头）：红瓶站里铜列贴矿、铜板链路 37–48 格，换个顺序可能总带长更短，但差的是几十格带，不影响达标。

**算法题**：候选排序、分支定界、碰撞与保留格、路由失败后的回退。

## 6. 契约这轮缺了什么

本任务里**没有**一处为了放置或路由回头查布局；放置只读契约（`link_ends` 与路由器同源）。补的字段：无（现有字段够放置用）。但有三处要说明：

1. **启动 / 缓冲填满时间**（3a §6 第 8 条）——第一次真的卡住一个站：上游按产能跑、下游按需取，盈余灌满链路带要 1000–2700 s，窗口 420 s 里测到的是产能不是稳态（迭代 1 上游 +25…30%）。站点层用 `fill_time` 顶替：链路带格 + **消费单元自己的带格**（这一项是从单元布局里数的——测量用，不是路由用，但严格说这就是契约缺的"单元内部缓冲量"）÷ 盈余。建议下一轮给 `Interface` 加 `buffer_items`（口后到最后一个取料点之间的带容量），`fill_time` 就不用看布局。
2. **电功率**：没卡住（电源是夹具）；真实部署要按功率选电源仍缺。
3. **衰减曲线**：没卡住——`choose_mining` 按窗口长度抬 `min_ore_amount_per_drill`，窗口被填充时间拉长时重新规划一遍即可（`red_science_rows` 这么做了）。

另一个口径问题不是契约而是**测量**：力统计按物料计数，几个单元消耗同一物料时按口判定没有意义，改成合并一行（§迭代 2 口径对照）。

## 8. 任务书不清楚的地方

- "红瓶的输入是一条带两道"——求解器默认时间盒给的周期是两条带（齿轮走铜带左道），只有短时间盒才给"两种板共一条带"。任务书的前提来自旧记录，执行者要先核实；两种契约路由器都接了。
- "现有 flat、real-map 实测结果不变"：放置规则换掉手写锚点后布局必然变，"结果不变"只能理解为产率在噪声内一致（同一布局两次实测本来就差 0.1%）；本记录把旧新数都列出。另外 real-map 的预热从 120 s 变成 622 s 是规则带来的，板从 99.6% 变成 100%。
- "6a 之后已知的回归 7.5 → 6.5"：本分支不存在（6a 迭代 8 已修），任务书把 exp 分支的状态当成了主线状态。
- 验收"矿、板、瓶偏差 ≤ 2%"没说煤；煤是整块量化，本记录按不在判据里处理但如实给出。
- 存档是否要含夹具（无限箱、能量接口）：保留的是测量用站点，含夹具；人在客户端打开看到的就是实测的那一张。

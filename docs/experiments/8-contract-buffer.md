# 阶段 8 任务 B：契约 `buffer_items`，启动时间由契约推导

任务书 `docs/plan-phase8.md` §3。分支 `phase8/contract-buffer`（worktree `/home/user/wt-8b`）。不起 headless 服务器，只做离线验证与单元测试；`characterization/*` 不动。执行者：Sonnet（medium）。

## 0. 结论先行

- 字段：`Interface.buffer_items: float | None`（物品口必填）= 单元自己的那一段带完全堵住时、在该口实际用的道上能容纳的件数（带格数 × `belt_items_per_tile` × 道份额）。输入口数到带末端，输出口数从第一个有东西落上来的格到口格。
- 三个家族和源 / 汇夹具都填；`validate` 的 `contract.buffer` 用遍历独立重数一遍；`site_sweep.fill_time` 只读两端口的 `buffer_items` 与路由结果。
- 口径变了：旧算法数"消费者单元的全部带格"（偏大）而漏了生产者的输出带；新算法按链路只数这条链路上的三段。预热变短（红瓶 1/s 3000 s → 约 1960 s，0.5/s 3600 s → 约 2560 s，real-map 622 s → 约 387 s），不够的风险用一个两级填充模型核对过（§4）。
- 实测未重做（本任务不起服务器）：合并后由任务 A 统一跑 headless，红瓶两档、real-map 的实测应在噪声内不变。

## 1. 先在纸上排除整族（规则 1）

要解决的是：`fill_time` 要一个"这条链路上有多少件要灌"，而现在它从 `units[n].layout` 数消费单元的全部带格。

| 族 | 做法 | 结论 |
| --- | --- | --- |
| A | 留在站点层，改成从消费单元布局里只数这个口的那条带（站点层遍历） | 排除：仍然读 `layout`，任务目标就是不读；也解决不了生产者的输出带 |
| B | 契约上每个物品口一个标量（件数） | **采用**：量是单元内在的（只取决于单元几何和口用的道），与邻居无关，可在生成时一次算好；镜像 / 旋转 / 平移不变 |
| C | 件数 + 传输延迟（第一件产物到口要走多远）两个字段 | 排除延迟：量级是带速度下走完几十格，几十秒，对 1000–3000 s 的填满是 1–2%，被 `FILL_FACTOR` 的 25% 和基础 240 s 吃掉；"填满"与"延迟"是两件事，有需要再加一个字段 |
| D | 按道分开的两个数（左 / 右） | 排除：一个口只用一组道（`lane`），共用一条带的两个口（矿 / 煤）各有各的字段；需要的折算（生产者只占一道而宿口两道）只是一个比值，由 `lane_share` 在站点层算 |
| E | 契约里直接给"填满秒数" | 排除：秒数 = 件数 ÷ 盈余，盈余取决于邻居和力状态（研究），不是单元的内在量 |
| F | 只给输入口 | 排除：生产者只在自己的输出带堵满之后才开始限产；旧算法漏了这一段（采矿带 15–20 格） |
| G | 输入口只数到最后一个取料点（任务书的字面） | 偏离：越过最后取料点的物品会停在带尾，要先填满那一截，带才会一路堵回口；数到末端才是"完全堵住"。冶炼列这一截是 1 格 |

字段名 `buffer_items` 沿用任务书；语义写进 `docs/plan-phase3a.md` §6 第 8 条的"已实现（阶段 8）"。

## 2. 实现

- `layout/model.py`：`Interface.buffer_items`。
- `geom/belt.py`：`lane_share(gd, lane)`（`left` / `right` 取 `1 / belt_lanes`，否则 1）、`run_items(gd, tiles, lane)`；数值（每格件数、道数）只来自种子。
- `layout/belt_run.py`（新）：`run_tiles(layout, gd, tile, role)`，从布局里独立遍历出口后（输入）或口前（输出）的带格。输入：沿流向可达的带格（地下带配对，只数两端）。输出：能流进口格的带格，从第一个落点（插件 / 钻机的落点）起；没有落点的带（装载机供料）整条算。
- `layout/validate.py`：`contract.buffer`——物品口缺 `buffer_items`，或与 `run_tiles` × 每格件数 × 道份额不一致。
- 生成器：
  - 冶炼列（公式）：输入 = 带长；输出 = 带长 − 第一个炉子的插件列（`length - col`）；矿口 / 煤口各按自己的道。
  - 采矿（公式，在 `_unit` 里已有的"从口往上游走输出带"的循环上）：数到最远一个钻机落点，只数带上有带实体的格（杆位被地下带跨过，不数）。
  - 直插链（遍历）：周期里的带含地下带，起点由求解器定，按平铺后的布局用 `belt_run.run_tiles` 数。
  - 夹具：源 / 汇各一格带（装载机一侧）。
- `site_sweep.fill_time`：链路缓冲 = 源口 `buffer_items` + 路由带格（`conn.routes` 里的带 / 地下带）× 每格件数 × 生产者占的道份额 + 宿口 `buffer_items` × min(1, 生产者道份额 / 宿口道份额)；除以盈余，取最大。`details` 里多一个 `parts: {out, route, in}`。函数体里没有 `layout`（测试里用 `inspect.getsource` 断言）。

## 4. 口径对照（规则 3）

旧定义：缓冲 = (链路路由格 + **消费单元自己的全部带格**，含输出带与别的输入带) × 每格件数 × 生产者道份额。
新定义：缓冲 = 生产者输出口 `buffer_items` + 路由格 × 每格件数 × 生产者道份额 + 消费者输入口 `buffer_items`（折算道份额）。

真实地图的地形快照不能离线重建（没有服务器），所以给两张表：

**表 1：记录的旧值（`characterization/site.jsonl` 里每行 `measured.fill_time`，真实布局）与新算法在"同一路由格数 + 离线生成的单元"上的值。** 路由格数取记录里的 `connection.routes`（真实布局）；两端 `buffer_items` 取离线在矿区位置画的矿区上生成的单元（矿区形状不同，钻机数按速率封顶所以带长基本一致；红瓶链是新解的，求解器有时间盒，布局可能与记录行有出入）。预热 = 基础 + 1.25 × 秒数，上限 3600（基础：real-map 120、红瓶 240、flat 60）。

| | iron-plate | 0.250 | 308 | 1232 | 220（32 + 128 + 60） | 880 |

| 场景 | 旧秒数 → `warmup_s` | 新秒数 → `warmup_s` | 最慢链路（新） |

两张表的结论一致：新口径下秒数下降 30–50%，原因有两处：

1. 旧算法数的是消费单元的**全部**带格：红瓶链的三个输入带和输出带，冶炼列的输入带（矿和煤同一条）与输出带，每条链路都这样；新算法只数这条链路的三段。
2. 旧算法漏了生产者的输出带；采矿的输出带（real-map 152 件）现在数进去了，这使 ore 链路在新算法里没有降到很低，也是 copper-ore 0.5 档（旧 44 → 新 44）几乎不变的原因（那里的采矿带只有一格）。

**为什么变短的预热仍然够**：预热 = 基础 + 1.25 × 填满秒数，余量是新口径下的 25% 加上基础 240 s。新口径数的件数是这条链路上物品真的要灌的三段，没有多数也没有漏数。另外 `fill_time` 取各链路的最大值而不是和，我用一个两级的填充模型核了一下（矿 → 矿带缓冲 → 冶炼列满速 → 板链路缓冲 → 链按需取）：冶炼列在板链路没堵满前按满速跑，这时矿带的盈余只有"矿产能 − 冶炼列满速"，比 `fill_time` 用的"矿产能 − 实取"小得多。四条板链路（表 1 的件数）整站稳定的时刻分别是 0.5 档铜 1856 s（= 板链路自己的 1856）、0.5 档铁 920 s（板链路 880，多 40 s）、1 档铜 1376 s、1 档铁 1216 s——与 `fill_time` 一致或多出 5% 以内，在 25% 余量之内。（这一步是模型推算，不是实测；实测要等合并后统一跑 headless，红瓶两档与 real-map 的上游矿 / 板读数应在 ≤ 2% 内。）

## 6. 契约这轮缺了什么

- `fill_time` 经 `flows` 调 `CAPACITY` 里各家族的吞吐预测器，直插链的 `dc.predict` 读自己的布局（机器和插件计数）。这是**吞吐**的预测，不是缓冲；`fill_time` 函数体本身不读。如果要整条预测链路也不读布局，要把单元吞吐也放进契约（家族预测器已经在 `meta` 之外读布局），这是下一步的事，不在本任务内。
- 仍然只数"最大的一条链路"：几条链路的填满是有先后的，我用两级模型核对过这几个站不会因此变长，但多级链（绿瓶站，板 → 绿板 → 绿瓶）要重新核。
- 衰减曲线和机器输入槽里的几件仍然没有进契约。
- 一个潜在的偏差来源：`drawn` 用的是冶炼列的**实取**（链堵满之后的），而填充期间冶炼列满速跑，矿带盈余更小；上面的两级模型显示不影响这四个站，但 `fill_time` 本身没有处理它。

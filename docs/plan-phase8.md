# 阶段 8：绿瓶站、判断题交给 agent、契约缓冲量、求解器模型瘦身

接续 `docs/plan-phase7.md` 与两份记录（`docs/experiments/7-red-science-site.md`、`7-solver-speed.md`）。三个任务：A 是实验主体，B 是小而确定的工程，C 是独立实验。都按 `docs/plan-phase6a.md` 的实验规则加 `plan-phase7.md` §4 的三条执行（只给目标、约束、工具与验收，不给排法；先在纸上排除整族再动手；相邻 sweep 不退化；指标语义变了给新旧口径），全程记录到 `docs/experiments/8-<task>.md`。

## 1. 动机

阶段 7 把站点层做到了"两矿 → 两列 → 红瓶，无手写坐标，实测 0%"，并给出两个结论：容器不需要；放置里真正的判断题（带长预算、占矿代价、转弯权重、优先级）已经从算法里剥出来放进 `PlaceCosts`，选矿则还是"每种矿取离原点最近的一个"。6a 复现实验给出的分工是：弱模型胜任"明确目标 → 通过不变量的代码"，强模型的溢价在判断与验收口径。这两条合起来指向同一步：**让 agent 真的去做判断题，用一个比红瓶站多一层、第一次出现分流的站点来检验**。

另外两件事各自独立：红瓶站第一次被"缓冲填满时间"卡住，站点层用 `fill_time` 从布局数带格顶替，契约仍缺 `buffer_items`；7B 的否定结论是"要快只能靠更小的模型"，驱动与参数都排除了。

最终目标不变：每一步做扎实，火箭是水到渠成的事。

## 2. 任务 A：绿瓶站 + 选址与放置的判断交给 agent

### 目标

在正常生成的地图（`config/ore-map-gen-settings.json`，同一 seed）上，从铁、铜矿区出发，经冶炼列与**绿板直插链**（中间产物），供一个绿瓶直插链，实测绿瓶产率达到契约，两档（0.5/s、1/s）。整条链路由一条命令完成，无手写坐标。站点变成四层（矿 → 板 → 绿板 → 绿瓶）；铁板第一次有**两个消费者**（绿板链和绿瓶链都吃铁板）——这是本库第一次需要"一个输出去两处"。

同时，把站点里的**判断题**做成 agent 的接口并真的交给 agent 回答：

1. **选矿**：每种矿区的候选不止一个（半径 150 的快照里有多个铁矿、铜矿），哪一个合适是判断题：储量、离出生点与离另一种矿的距离、混矿、周围的悬崖与水、形状、以及采矿生成器在它上面能出多少（钻机数、带速率、`first_dry_s_lower_bound`）。现状 `nearest_patch(min_tiles=50)` 是一条规则。
2. **放置偏好**：`PlaceCosts`（步、转弯、绕回、占资源格、窗口余量）与放置顺序的优先级，7A 记录 §5 已列为判断题，默认值是执行者当时拍的。

### 执行者自己核实的现状

- 绿瓶链（4b 迭代 C5–C8，`direct_chain_sweep.py` 的 `green` 用例）：绿板上带（`belt_inputs=("electronic-circuit",)`）、需要长臂爪、`max_lane_consumers=6`，一个周期 6 台绿瓶机 + 爪子机 + 传送带机 + 齿轮机（29×8），0.5/s 一个周期、1/s 两个周期不重解；60 s 时间盒内首解 35 s 左右（不证明）。它的**输入口有几条带、各占哪些道、铁与绿板的 `MinRate`** 由执行者生成后核实——任务书不替你数（7A 的教训：任务书按旧记录说"一条带两道"，实际是两条带）。
- 绿板链（3:2，`electronic-circuit`）：输入铁板、铜板，4a/4b 的基本用例，秒级求解。
- `site_sweep.red_science_plan` 对链的每个板输入口各配一条冶炼列、各配一个矿；`smelting_for` 按下游口的 `MinRate` 定列；`choose_mining` 一条带、上限取列的矿口 `MinRate`；`add_fixtures` 给没接链路的口配夹具。绿板是可造的中间产物，不是板——"谁来供某种物料"现在没有通用规则。
- 分流：路由器会"多个生产者汇入一个消费者"，不会"一个生产者分给多个消费者"；库里没有分离器 / 平衡器单元。采矿生成器支持多条带（`max_belts`），每条带一个输出口。
- `site_measure.real_map_prepare` 每种矿只取 `nearest_patch`，清障区取所选矿区的并集 ±45；选别的矿区意味着清障区与快照范围要跟着候选走。
- 一次 CP-SAT 求解会把 4 核里的 1.5 核占满 35–60 s；任务 C 同时在这台机器上跑求解器实验，墙钟会抖，游戏内按 tick 的实测不受影响。

### 范围外

信标、液体、科技研究、UPS、真实玩家存档、`buffer_items`（任务 B 做；A 在 B 合并前照旧用 `fill_time`，合并后切换）。

### 判断题交给 agent 的形式（要求，不是排法）

- 站点层把每个判断题做成一个**结构化的问题**：候选 + 事实 + 默认答案 + 每个权重的含义。事实只能来自地形快照、契约、以及对候选跑生成器得到的数（钻机数、带速率、采空下界）。问题里**没有坐标让 agent 填**：选矿是从候选里挑，放置偏好是权重与优先级；agent 的答案不含任何格坐标，放置仍全由规则给出。
- 答案是一个可提交的文件（建议 `config/decisions/<scenario>.json` 之类，格式执行者定），带来源（谁答的、哪个模型、何时、依据）。`fgen sweep site` 读它；**没有答案文件时行为与现在逐字节相同**（红瓶三个场景的 `render` 不变）。特征化表要可复现，所以答案进仓库，不在 sweep 里现场问模型。
- 回答者至少三种：(i) 现行规则（默认）；(ii) 一个弱模型（Haiku 或 Sonnet，只给问题文件与读题所需的说明，不给站点代码），(iii) 执行者自己。红瓶站与绿瓶站各问一遍（红瓶站是对照：7A 的默认答案已经达标，看判断改了什么）。
- 对照用**agent 改不了语义的硬指标**：路由的带格与地下带数、钻机数与 `first_dry_s_lower_bound`、`fill_time`、放置重试次数、实测产率与偏差；不用生成器自报的诊断量。

## 3. 任务 B：契约 `buffer_items`，启动时间由契约推导

**目标**：给 `Interface` 加缓冲量字段，使 `site_sweep.fill_time` 不再读任何单元的 `layout`，启动 / 缓冲填满时间完全由契约 + 路由结果推导。小而确定。

**现状**（`7-red-science-site.md` §6 第 1 条）：`fill_time` 对每条"源能给得比取得多"的链路算 `(链路带格 + 消费单元自己的全部带格) × 每格件数 × 道份额 ÷ 盈余`，其中"消费单元自己的带格"是从 `units[n].layout.placements` 里数的，而且数的是单元里**所有**带（含输出带与别的输入带），偏大。

**要求**：

- 字段语义由执行者定并写进 `docs/plan-phase3a.md` §6 第 8 条后面的"已实现"说明。至少覆盖：输入口——口后到最后一个取料点之间、这条带（按口实际用的道）能容纳的件数；输出口——是否需要、含义是什么由执行者论证（第一件产物到口要走多远，与"填满"是两件事）。
- 三个生成器家族（冶炼列、直插链、采矿）与全部夹具填它；数值从各自的几何推导，不写死。
- `validate` 加契约一致性检查（口的 `buffer_items` 与口格起沿带可达的带格数一致），与现有 `contract.*` 检查同一风格。
- `fill_time` 改为只读契约与路由；`grep` 不到它读 `layout`。
- **口径对照（规则 3）**：三个现有场景（`flat`、`real-map`、`red-science-0.5/1`）旧算法与新算法的 `buffer_items`、`seconds`、推出的 `warmup_s` 并列成表写进记录。预热变短是允许的，但要说明为什么仍足够（新口径下填满之后再加 `FILL_FACTOR` 的余量）。
- 不起服务器：本任务只做离线验证与单元测试；headless 全量由合并后统一跑。不改 `characterization/*`（`fgen sweep site` 不带 `--measure` 重新生成时 `render` 不变，实测行保留）。

**验收**：`uv run --extra solver pytest -m "not headless"` 全绿且新增字段有测试；`grep -n "layout" src/fgen/gen/site_sweep.py` 里 `fill_time` 一段为空；口径对照表在 `docs/experiments/8-contract-buffer.md`；`fgen sweep site`（不带 `--measure`）重新生成后 `site.jsonl` 的 `render` 与 `measured` 不变。

## 4. 任务 C：求解器模型瘦身（独立实验）

**目标**：7B 留下的结论是"首解 35 s 是单个 32×8 模型 presolve + 首解的下界，并行与参数都到不了 10 s；要更小的模型"。本任务做模型本身。数字目标沿用 7B 未达到的部分：

- 绿瓶首个可行解 ≤ 10 s（4 核、`--procs 1`、按 `cp_det_ms` 与墙钟两个口径都给）；其余用例首解不变慢。
- 12 台机器周期（`solver_time` 的 `green-12-anytime` 用例已写好）10 分钟时间盒内给出可行解并说明证明进度。
- 红瓶 1:10 的 600 s 证明：能不能证完，给结论。

**执行者自定手段**，7B 记录 §"待办"列了两个候选（流变量按槽位而非锚点对；首解限制在"机器只在整行带的紧邻两行"的子域作启发式首解、证明路径不动）和昨天没动手的两个（同高度分组；带行与机器行拆成两阶段）。规则 1：先在纸上估每个方向省多少变量 / 多少秒，排除了哪些、为什么，再动手。7B 已排除的（宽度有界可行性模型、CP-SAT 参数、定点尺度、多 worker）不要再试。

**约束与验收**：

| 项 | 判据 |
| --- | --- |
| 正确性 | 与穷尽搜索后端的对拍用例全部一致；"已知可行周期必须能找到"的回归全过；`direct_chain.jsonl`、`fluid_chain.jsonl` 的 prove 行重跑后蓝图不变（实测行保留）；`palette.jsonl` 的随时可用行不变、prove 行按 7B 的待办给 `prove=True` 行按 `PROCS` 放宽墙钟后重跑 |

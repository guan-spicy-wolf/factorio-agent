# 阶段 4b 实验：CP-SAT 后端对比、运行时状态、红瓶与绿瓶直插链

接续 `docs/plan-phase4a.md`。实验规则沿用 `docs/plan-phase6a.md`（不给排法、自行迭代、全程记录到 `docs/experiments/4b-cpsat-and-science.md`）。4a 回答了"约束难不难写"（不难）和"穷尽搜索够不够快"（够），但没回答**每个新家族是否都要重写一遍搜索**。本轮沿这条轴测。

## 1. 任务 A：CP-SAT 后端，与穷尽搜索对拍

- 把 OR-Tools 作为**可选依赖**（`uv add --optional solver ortools`，核心库默认安装仍零依赖；没装时后端不可用并给出清楚提示）。
- 新后端实现与现有求解器**相同的接口**（`CycleSpec → Period`），约束用 CP-SAT 变量声明式表达；仍用 `check_period` 与 `validate` 做最终裁判。
- 在 4a 的全部 8 个变体上对拍，表格记录：最优面积是否一致、是否同样找到 108 的周期、是否同样证明 R=6 黄带不可行、求解时间、**家族专属代码行数**（穷尽搜索版 vs CP-SAT 版，只算约束与搜索，不算共用的周期模型）、写到第一个正确解的迭代次数。
- 两个后端对同一规格给出不同最优面积时，视为其中一个有 bug，必须查清并记录是哪个、为什么。

## 2. 任务 B：运行时状态进入数据层

- 测试服务器在实测前 `force.research_all_technologies()`（全科技解锁），取代 4a 里"按需解锁配方"的做法。
- 新增数据层第三个来源 `RuntimeState`：从 force 读取并记录爪子手持加成（普通与集装分开）、采矿产能加成、科研状态等会影响吞吐的量。`gen/throughput.py` 的预测必须按 `RuntimeState` 算，不再把手持量当常数；`characterization/*.jsonl` 每条实测记录附带当时的 `RuntimeState`。
- 全科技下重新实测冶炼列、采矿、整站、直插链四份 characterization，预测与实测仍需一致；不一致的地方是预测模型缺的项，修模型，不改排法。实测里要注明：全科技后哪些数字变了、为什么（例如集装爪手持量）。

## 3. 任务 C：新配方——红瓶，再做绿瓶

- 红瓶（automation-science-pack）：铜板 + 齿轮，齿轮由直插供应。配比**不整齐**（一台齿轮机远多于一台红瓶机所需），正是 `design.md` 说的"近似整数比让一侧略过剩，或退化为两段行用带子传中间产物"的情形。由执行者决定周期怎么定义、过剩怎么表达进契约、什么时候退回用带子。
- 绿瓶（logistic-science-pack）：爪子 + 传送带，两者都是中间产物且各自还有中间产物（齿轮、绿板），是三级树。做完红瓶再做，作为对"配方树更深时周期定义是否还成立"的检验。
- 两个配方都走 `direct_chain` 家族（允许扩展 `CycleSpec` 使其能表达多级树与过剩），**优先用 CP-SAT 后端**；穷尽搜索后端能跑也对拍，跑不动就记录原因，这本身是任务 A 的证据。
- 每个配方：目标产率取 0.5、1、2 瓶/秒；夹具供原料；实测达标；写入 `characterization/direct_chain.{jsonl,md}`。
- 记录每个新配方"家族专属新增代码"有多少行、落在哪些文件，与 4a 的 1300 行搜索对照。

## 4. 验收

| 项 | 判据 |
| --- | --- |
| A | 8 个变体两后端最优面积一致、108 与 R=6 结论一致；对拍表与代码行数表进实验记录 |
| B | `RuntimeState` 进入预测；四份 characterization 在全科技下重测并附带状态；预测与实测偏差 ≤ 2% |
| C | 红瓶 3 档产率通过 validate 并实测达标；绿瓶至少 1 档达标或记录清楚卡在哪；新家族代码行数记录 |
| 记录 | 最后一节回答："新家族是否还要手写搜索？CP-SAT 版每个家族专属代码有多少？该把哪个后端设为默认？" |

## 5. 约束

- 不放宽不变量；不写死数字或 if 实体名；不改冶炼列与采矿排法。
- 不做信标、模块、流体机器（下一轮）。
- 两个后端都要在 `uv run pytest -m "not headless"` 里有测试；OR-Tools 未安装时相关测试 skip 而不是失败。

# 阶段 7：多单元站点（红瓶站）与求解器效率

接续 `docs/design.md`（第二版）"未做"一节。两个任务并行、互不依赖，都按 `docs/plan-phase6a.md` 的实验规则执行（只给目标、约束、工具与验收，不给排法；全程记录到 `docs/experiments/7-<task>.md`），并加上 `docs/experiments/6a-replication.md` 得出的三条新规则（见 §4）。

## 1. 动机

六轮实验把单个单元做到了"生成器产出、预测精确、实测 0% 偏差"，但站点层只到过"一个矿区 + 一个冶炼列"：场景函数里写死了锚点、链路、单元数和家族名（`gen/site_sweep.py`、`sim/site_measure.py`）。方案留下的问题——容器要不要、契约够不够、放置谁来定——都要等多单元站点出现才能回答。另一头，周期求解器的首解除绿瓶 53 s 外都在秒级，但证明最小要 20–40 分钟，更大的周期（12 台机器）没跑过；设计 v2 已经点名"把同高度的带分组合进一个模型"，但没人做。

本阶段同时回答这两个问题。最终目标不变：每一步都做扎实，火箭是水到渠成的事。

## 2. 任务 A：红瓶站（真实地图，端到端）

**目标**：在正常生成的地图（`config/ore-map-gen-settings.json`）上，从**两个矿区**（铁、铜）出发，经两条冶炼列，供一个红瓶直插链，实测红瓶产率达到契约。整条链路——选矿、清障、生成、放置、路由、部署、实测——由一条命令完成，中间没有人手写的坐标或锚点。

**现状里要泛化掉的东西**（执行者自己核实，调研见 `6a-replication.md` 之后的站点调研摘要）：

- `site_measure.real_map_row` 只找离原点最近的一个铁矿；`choose_mining` 只出一条带，上限取冶炼列道容量；场景固定一个冶炼列；`predict` 只认两种家族；`explain_real` 按 `mine#` 前缀找口；部署把全站当一张蓝图放在 (0,0)。
- 放置：`place.find_spot` 从**手写锚点**螺旋扫描。本任务要一个由链路驱动的放置规则（下游单元放在上游输出口的"合理范围"内，范围由带长成本、地形和已占格决定），锚点由算法给。容器（`Column/Row`）要不要，由执行者按实际需要决定并在记录里说明理由——这是设计 v2 悬而未决的问题，本任务要给出答案。
- 直插链从未作为站点里由真实单元供料的下游单元被路由过，只接过夹具。红瓶的输入是一条带两道（铁板 / 铜板，`LaneMaterial` 挂在 `PortGroup` 上）；两条冶炼列各出一道，要侧向汇入同一条带的不同道——路由器现在"同一个消费者口可以有多个生产者分别侧向汇入"，是否覆盖"两个生产者各占一道"由执行者核实。
- 铜矿、铜板：种子数据与夹具是否已覆盖，不够就按 CLAUDE.md 的流程改 `extract_seed.py` 的 `ADD` 表重新生成。

**范围外**：平衡器（红瓶不需要一分多）、液体、信标、科技研究、UPS。

**验收**：

| 项 | 判据 |
| --- | --- |
| 端到端 | `uv run --extra solver fgen sweep site --measure --real-map` 新增 `red-science` 场景：红瓶实测 ≥ 契约的 98%，稳定段按 tick 计 |
| 产率 | 红瓶契约目标 0.5/s 与 1/s 两档；两档的矿、板、瓶预测与实测偏差都 ≤ 2% |
| 无手写坐标 | 场景函数里 `grep` 不到字面坐标与 `neighbor(d, N)` 式锚点；放置全部由规则给出，规则有单元测试（手写 `Terrain`） |
| 不退化 | 现有 `flat`、`real-map` 两个场景的实测结果不变（7.5/s 整站那条 6a 之后已知的回归一并处理）；`fgen sweep mining/smelting/direct-chain` 不重解、不变 |
| 契约 | 本任务消费契约时每发现一处"不得不回头查布局"，记下来并补字段；仍缺的（电功率、启动时间、衰减曲线）本任务不补，但要写明红瓶站有没有被它们卡住 |
| 存档 | 1/s 那档用 `--keep-save` 保留存档并 `bin/publish-save.sh` 推到 `saves` 分支，记录里给文件名，人要能在本地客户端打开 |
| 记录 | 末节回答：容器要不要？放置规则的输入是什么、哪些决定其实是判断题（应交给 agent）而不是算法题？契约这轮又缺了什么？|

## 3. 任务 B：周期求解器效率

**目标**：在不改变解的集合（可行性、最优值）的前提下，把 CP-SAT 周期求解的时间压下来。数字目标：

- 首个可行解：绿瓶 52.7 s → ≤ 10 s；其余保持 ≤ 6.4 s 或更快。
- 证明最小：4c 表里跑完的行（3:2 全调色板 1086 s、绿瓶 1861 s）时间减半；600 s 内未证完的行（红瓶 1:10）给出是否能证的结论。
- 12 台机器的周期（执行者选一个合理配方）在 10 分钟时间盒内给出可行解并说明证明进度。

**执行者自定手段**。已知事实（`docs/experiments/4b-cpsat-and-science.md`、`4c-anytime-palette.md`、`solve/cpsat.py` 模块 docstring）：时间大头在建模与 presolve 而非搜索，多 worker 几乎无益；外层逐尺寸 (W,H) 枚举、每个模型各付一次 presolve；长臂爪让槽位与用途成倍增加；已有的对称处理只有机器不分身份与 y 镜像；没有分组与分解。候选方向有分组同高度的带、更强的对称破除、跨尺寸复用模型（变上界而不是重建）、从 `repeat_period` 的种子做提示（hint）、把带行与机器行分两阶段解——选哪个、按什么顺序试，先在纸上估算每个方向能省多少再动手（§4 规则 1）。

**验收**：

| 项 | 判据 |
| --- | --- |
| 正确性 | 与穷尽搜索后端的对拍用例全部一致；`characterization/direct_chain.jsonl`、`fluid_chain.jsonl`、`palette.jsonl` 的 prove 行重跑后蓝图不变（实测行保留）；回归用例"已知可行周期必须能找到"全过 |
| 时间 | 上面三条数字目标，在同一台机器上前后对照（4 核容器），表格进 `characterization/solver_time.{jsonl,md}`（新 sweep，不手改） |
| 不可满足核 | 对一条已知不可行行（红瓶 1:3）给出不可满足核或证明时间对照 |
| 记录 | 每个尝试过的方向：预估收益、实际收益、为什么留或弃 |

## 4. 实验规则（在 6a 规则之上新增）

1. **先在纸上排除整族，再动手**。动手前写下你能想到的每一族做法及其上限（任务 A：放置规则的几族；任务 B：每个效率方向能省的时间量级），并说明排除了哪些、为什么。这是 `6a-replication.md` 的结论：解的质量差在这一步，不在编码。
2. **验收包含"相邻 sweep 不退化"**。改了生成器或求解器，所有以它为输入的特征化表都要重跑并对照；退化就是不达标，哪怕任务书没点名那张表。
3. **指标语义变了要给新旧口径对照**。任何因为结构改变而失去原意义的指标（6a 的 `pole_slot`），记录里要写新定义、旧定义、两者在同一组用例上的数值。
4. 其余沿用 6a：不放宽不变量、不写死数字、不 if 实体名、失败也记、结束时统计迭代次数 / `validate` 失败 / 实测不达标 / 耗时。

## 5. 约束

- 全部按 CLAUDE.md：只用 `uv`，数值只在种子数据，服务器一次一个实例，特征化表只由 sweep 生成。
- 两个任务各一个 worktree、各一个执行者，任务 B 不需要服务器；任务 A 的实测与任务 B 的 sweep 不能同时跑 headless。
- 任务 A 完成后 `docs/design.md`"组件树与容器""实施阶段"两节按结论修订；任务 B 完成后"风险与开放问题"的"求解规模"一条修订。

# 阶段 3a 实施任务书：清障、夹具泛化与单元间连接

接续 `docs/plan-phase2.md`。目的不是把阶段 3 全部做完，而是用最便宜的方式检验**接口契约是否够用**：让一个确定性的连接算法只读契约，把两个单元用带子、管道、电杆接起来，在真实地形上仿真达标。资源按无限供应（夹具）给，不做选址 agent，不做真实存档部署。本文与 `design.md` 冲突时以本文为准。

## 1. 复盘结论对本阶段的影响

- 契约里的 `assumptions` 目前是字符串。本阶段把连接算法会用到的几条变成**可检查的结构化字段**（见 §3.1），字符串只留给人看。
- 锚定单元的速率随时间衰减。本阶段连接算法只用初始速率，但契约里要能放 `rate_profile`（初始速率、估计采空时间），由采矿生成器填。
- 仿真测试 ≠ 真实部署。本阶段全部是仿真：正常生成的地图 + 夹具 + 临时存档。

## 2. 技术约定

沿用阶段 0–2 全部约定。路由算法是纯函数，输入 `Terrain` 快照 + 已放置单元 + 连接请求，输出 `Layout`；单元测试用手写 `Terrain`，不起服务器。所有距离（地下带/地下管跨度、拉线距离、供电区）从种子取。

## 3. 模块

  site/

    place.py           最小放置规则：在给定锚点附近找能放下单元的空矩形（§3.5）
  route/

    astar.py           带转向代价的网格 A*（4 邻接，支持"跳跃边"表示地下段）
    belt.py            带子路由（含地下带、侧向汇入）
    pipe.py            管道路由（含地下管、邻接隔离）
    power.py           电杆链路由与多单元并网
    connect.py         connect(site) -> Layout + 诊断；先电、后管、后带（或按冲突重排）
  sim/

### 3.1 契约升级（`layout/model.py`）

`Interface` 增加：

- `rate_profile: RateProfile | None`：`initial`（= 现在的 `rate`）、`depletion_s_lower_bound`（锚定单元填，自由单元 None）。
- `requires: tuple[Predicate, ...]`：结构化前置条件，连接算法与夹具都要校验。先定义这几种：
  - `LaneMaterial(lane, material)`：该带道上只能是这种物料（冶炼列的"矿在左、煤在右"）。
  - `MinRate(value)`：输入至少这么多才达标（= 目标产率反推）。
  - `Compressed()`：假设输入满压缩（只记录，不校验）。
- `Interface.world(origin, transform)`：给出世界坐标与方向（放置后的接口）。

现有生成器（冶炼列、采矿）改为填这些字段；旧的 `assumptions` 字符串保留。

### 3.2 清障（`sim/clear.py`）

`clear_obstacles(rcon, area) -> dict`：销毁 `tree`、`simple-entity`（石头）、`item-entity`、`corpse` 类实体，返回各类计数；**不动**资源、悬崖、水、玩家建筑。`RconTerrain.snapshot` 之后再清障会让快照失真，所以流程固定为：清障 → 快照 → 生成/路由 → 部署。悬崖在快照里是不可建格，路由绕行。

### 3.3 夹具泛化（`sim/harness.py`）

- 源/汇/电源各表示为一个微型 `Unit`（`infinity-chest + loader` 的供料头、`loader + steel-chest` 的汇、`electric-energy-interface + 一根杆`），带自己的 `Interface`。这样连接算法对"夹具"和"单元"一视同仁：**夹具只是契约的另一端**。
- 分道供料：源头 Unit 的输出接口声明 `lane`，`LaneMaterial` 由路由用侧向汇入满足（§3.4）。
- 液体源/汇：`infinity-pipe`（设 `infinity_pipe_filter`，模式 `at-least` / `exactly`）；汇用 `infinity-pipe` 设为 0 或 `storage-tank` 读 `fluidbox`。先在实机确认 2.1 的字段名，记 VERIFY。

### 3.4 路由（`route/`）

通用：

- 网格 = 快照里可建、无水、未被任何单元或已路由实体占用的格；资源格可走但加代价；接口口正前方 k 格做保留带（防止别的路由把口堵住）。
- A*：4 邻接；代价 = 步数 + 转向惩罚；"跳跃边"表示地下段：从 `(t, d)` 跳到 `(t + n·d, d)`，`2 ≤ n ≤ max_distance + 1`，中间格不要求可走（可穿越水、悬崖、带子、管道），入口和出口格必须可走，代价 = 地下实体数 + 小惩罚。
- 输出 `Layout` 后对**整站**跑 `validate`，再按 `requires` 做契约校验。

**带子**（`route/belt.py`）：

- 直连：从生产者口沿其方向出发，到消费者口沿其方向进入（终点约束是"进入格 + 方向"）。两道物料不变。
- 侧向汇入（满足 `LaneMaterial`）：目标是消费者输入带上的某一格，从该带的左侧或右侧垂直汇入；汇入侧由要填的道决定（东向带填左道从北侧汇入，阶段 1 已实机核对）。多个生产者汇到同一条带时按道容量累计检查，超了报 `Infeasible`。
- 速率检查：`sum(initial rates) ≥ MinRate`，单道 ≤ 道容量，整带 ≤ 带容量；不满足给出建议（换带等级、分两条）。
- 带等级：取消费者接口所在带的等级，上游低等级时报警不报错。

**管道**（`route/pipe.py`）：

- 管 + 地下管，跨度 `max_underground_distance`。
- 邻接隔离：新管不能与任何非目标的液体连接点相对（复用 `fluid.unintended_adjacency`）；A* 把这类格标为不可走。
- 本阶段只测一条：`infinity-pipe` 源 → 隔着障碍 → `storage-tank` 汇，验证连通且 `fluidbox` 有量。

**电**（`route/power.py`）：

- 把所有单元的电接口（各自的第一根杆）和电源夹具并成一个网：按欧氏距离建 MST，每条边用一串杆铺路，杆间距 ≤ 两端中较小的 `maximum_wire_distance`，杆放在可走格上，放不下就沿边两侧找最近可走格；导出的蓝图写 `wires`（阶段 1 已有）。
- 验收：实机读 `electric_network_id` 全站唯一。

**冲突与顺序**（`route/connect.py`）：电杆占 1 格最灵活所以最后放；先带后管，或先管后带；任何一步失败就换顺序再试一次，仍失败抛 `Infeasible` 并指出是哪条链路、卡在哪一段。

### 3.5 最小放置规则（`site/place.py`）

不做选址 agent。给一个锚点和一个 Unit，在锚点附近螺旋扫描，找到第一个能放下 Unit 占地（加 1 格边距）的位置，可指定旋转/镜像候选。只服务本阶段测试。

### 3.6 整站仿真（`sim/site_measure.py`）

部署顺序：清障 → 快照 → 生成单元 → 放置 → 路由 → 部署全部 → 接夹具 → 跑 → 逐口实测。实测每个消费者输入口和最终输出口的速率，与契约（`MinRate`、`initial`）对比，写 `characterization/site.jsonl/.md`。

## 5. 不要做的事

- 不做选址 agent、不做任何 LLM 调用。
- 不做真实玩家存档的部署与备份回滚。
- 不做平衡器、不做多带合流到一条带以外的流量重分配。
- 不改冶炼列和采矿的排法（电杆占位问题另开任务）。
- 不追求路径最优，可达且合法即可。

## 6. 结果

M1–M6 全部完成（2026-10-24，headless 2.1.23）。测试 261 个：不起服务器 209 个约 25 秒，headless 52 个约 110 秒。实测见 `characterization/site.md`。

| 场景 | 契约 | 实测 |
| --- | --- | --- |
| 平地（M4）：7.5/s 石炉列，两个源夹具经侧向汇入供矿（左道）和煤（右道） | 矿 `MinRate` 7.5，煤 0.54，板 `initial` 7.5 | 矿 7.508，煤 0.525（整个计数的量化），板 7.5；电网 1 个 |
| 真实地图（M5）：seed 20261024 最近铁矿 → 一条带 15 台钻 → 11 格带路由侧向汇入 → 冶炼列；煤夹具汇入右道；一个电源夹具经 5 根杆并网 | 钻 `initial` 7.5，板 min(7.5, 7.5) 的 95% | 钻 7.5，板 7.456（99.4%）；差额是还在进炉子缓冲的矿 |

与任务书不同的地方：地下带跳跃取 2..`max_distance`（§4 实测），不是 `max_distance + 1`；采矿生成器没改，M5 的“产率接近 7.5”靠场景里的固定选择规则（四种轴向/流向里取不超过消费道容量的最大带速率，`site_sweep.choose_mining`）；`connect` 按“先带、后管、最后电”，失败时换成“先管、后带（失败链路先走）”重试一次。

### 接口契约够不够连接算法用

**够用，但有两处要回头看实体，还有几处靠约定或靠旁路。** 两个场景里，路由器只看接口的格、方向、带道、物料、`rate`/`rate_profile` 和 `requires`，就决定了直连还是侧向汇入、汇入哪一侧、能不能过容量检查、契约是否满足；`LaneMaterial` 和 `MinRate` 都是实际起作用的判据（错物料、超道容量的用例会被拒绝），整站 `validate` 通过，实测达标。

连接算法实际用到、但契约里没有的东西（建议下一阶段加进 `Interface`）：

1. **端口下的实体**：带等级（决定路由用什么带、地下带跨度、道容量）和电接口的杆种（决定拉线距离）都是从单元布局里“端口格上是什么实体”反查的。应加 `entity`（或 `belt` / `pole`）字段。
   **已实现（阶段 6a）**：`Interface.entity: str | None`——物品口是口格上的带类实体（带等级），电口是杆，液体口是承载连接的实体。路由器（消费者桩用的带、道容量、慢带警告）、电杆链（杆种与中心：`geom.footprint.center_at_tile(entity, tile)`）、夹具（源/汇用什么带、电源夹具用什么杆）都只读它；`route.belt.belt_at` 已删除。液体路由判断"自己的连接"也不再扫单元布局里的全部液体连接，只取链路两端接口（格 + 朝外方向）。不变量 `contract.entity` 检查它与口格上的实体一致。
2. **按道的速率**：采矿口 `lane="both"` 只给总速率，左右道各几台钻在 `meta` 里；直连时只能查整带容量，查不了单道。应加 `lane_rates`（或 `RateProfile` 按道）。
   **已实现（阶段 6a）**：`RateProfile.lanes`（按道的固定速率，相加等于 `initial`；按需供给时为每道上限），`Interface.lane_rate(lane)` 读取。采矿口按左右道钻机数填，冶炼列输出只有远道，源夹具两道各为道容量。路由器直连时按生产者的分道速率计入消费者各道（`both` 口不再按"每道至多一半"估算，只在生产者没给分道时才退回这个估算），侧向汇入时整股进所汇入的道。不变量 `contract.rate` 检查分道速率之和与所用道。
3. **按需供给**：夹具源的 `rate=None` 被约定为“要多少给多少”。这是语义重载，应在 `RateProfile` 里显式区分固定产率和按需（含上限）。
   **已实现（阶段 6a）**：`RateProfile.supply`：`"fixed"`（`initial` = `Interface.rate`）或 `"on_demand"`（`limit` 为上限，可为 None；`Interface.rate` 必须为 None）。源/汇夹具、液体夹具填 `on_demand`。路由器只认 `on_demand()`：没有画像、`rate=None` 的口不再被当成无限供给（`test_rate_none_is_not_on_demand`）。
4. **同一条带的多个口**：冶炼列的矿口和煤口是同一格上的两个接口，路由器靠“同格”把它们归成一个消费者、共用一个汇入桩。应有显式的“端口/带”分组，道要求挂在组上。
   **已实现（阶段 6a）**：`Interface.port_group` 引用 `Unit.groups` 里的 `PortGroup(name, requires)`；带道要求 `LaneMaterial` 挂在组上（冶炼列的 `feed` 组：左道矿、右道煤），每口自己的要求（`MinRate`、`Compressed`）留在口上。路由器按 `(单元, 组)` 归消费者，不再按格；校验报告里组要求记为 `row/feed`。镜像变换同时翻转组要求的道。不变量 `contract.group` 检查组存在且同组的口在同一格同一方向。
5. **端口前的空间要求**：侧向汇入需要在消费者上游补 2 格直带桩，再加两侧的汇入格；契约没说口前要多少空格、能不能直接在单元自己的带上侧向汇入。放置规则只好按固定的 `PORT_CLEARANCE` 留空。应加 `clearance` 或 `approach`（允许的进入方式与所需格数）。
   **已实现（阶段 6a）**：`Interface.space = PortSpace(approach, upstream)`：`approach` ∈ `direct` / `side` / `both`，`upstream` 是口前（输入口上游、输出口下游）要留的直线空格数。路由器 `link_mode` 按 `approach` 与 `lane` 决定直连或侧向汇入（`side` 但 `upstream` 不够放桩、或 `side` 口不指定单道都是 `Infeasible`），`reserve_ports` 保留 `upstream` 格；放置规则 `port_tiles` 留 `upstream` 格。`PORT_CLEARANCE`、`RESERVE` 常量已删除。约定数值 `PortSpace.item`：直连 2（路由第一节带 + 1 格引导），侧向汇入 3（`SIDE_LOAD_STUB` 2 格桩 + 1 格引导）。改成按口给数后两个整站的实体逐个相同（离线指纹），实测不变。
6. **液体口约定**：液体口的 `tile` = 带连接的实体格、`direction` = 朝外，输入输出同一约定（物品口的输入方向却是流向）。现在只写在 `route/pipe.py` 的说明里；液体还缺流量（`MinRate` 对液体未校验）和温度。
7. **电力需求**：电接口没有功率，电源夹具是无限电，路由只管连通。真实部署要按功率选电源和杆。
8. **启动/缓冲时间**：真实地图整站在供需相等时要 120 秒才稳定（平地 60 秒），契约里没有“填满需要多久/多少缓冲”，只能在实测里摸。`rate_profile` 只有初始速率和采空下界，本阶段没用到衰减曲线本身。

不需要进契约、留在布局里就好的东西：爪子与钻机的可达格、单元内部的带和管（路由器从合并布局里推出“别碰”的格），以及 `Compressed`（本阶段只记录，没有一处需要它）。
